## 1. 제품 개요

소담 AI 스튜디오는 한 줄의 아이디어에서 **영상 기획 → 스토리보드 이미지 → 편집 → 내보내기**로 이어지는 AI 콘텐츠 제작 서비스다.

이번 버전은 기존 **한 줄 텍스트 중심 영상 제작 흐름**을 그대로 유지하면서, 사용자가 자주 쓰는 캐릭터·제품·로고 등의 시각 자료를 개인 자산으로 축적하고 이미지·영상 제작에 반복 활용할 수 있는 **통합 크리에이티브 자산 구조**를 추가한다.

인증은 Google OAuth를 유지한다. 랜딩 페이지의 Google 로그인 버튼 **하단에 이용약관·개인정보처리방침 링크**를 노출하며, **로그인 자체가 암묵 동의**로 간주된다. 별도 동의 팝업/체크박스는 없다. 가입(=최초 로그인) 완료 시 **60크레딧**을 자동 지급한다. 오픈놀 마스터는 가입 사용자 목록을 확인하고 총 **60,000크레딧의 지급 누계 한도** 안에서 특정 사용자에게 크레딧을 지급할 수 있다.

### 1.1 한 줄 정의
"오픈놀 소속 크리에이터/소상공인이 Google로 로그인해 **기획 → 스토리보드 → 편집 → 내보내기** 워크플로우로 AI 영상 소재를 제작하고, 개인 자산(캐릭터/제품/로고/이미지)을 축적·재사용하며, 필요 시 마스터가 크레딧을 지급하는 관제형 SaaS."

### 1.2 현재 제공 범위 (스코프)

#### 영상 트랙
| 단계 | 코드 스텝 | 제공 여부 |
|------|-----------|-----------|
| 기획 | PLANNING | ✅ 제공 |
| 스토리보드 만들기 | VISUALIZING | ✅ 제공 |
| 편집 | ASSEMBLY | ✅ 제공 |
| 내보내기 (영상 제작) | PRODUCTION | ⛔ **게이팅 유지** — Kling 잔고 및 VEO 검증 후 재오픈 |

#### 신규 도입 기능
| 기능 | 설명 | 상태 |
|------|------|------|
| **자산 보관함** | 캐릭터·제품·로고·일반 이미지를 개인 자산으로 저장·관리 | ⬜ 설계 완료, 구현 필요 (§9.3) |
| **단건 이미지 만들기** | 영상 프로젝트와 독립된 이미지 1장 제작 화면 | ⬜ 설계 완료, 구현 필요 (§9.4) |
| **자산-영상 연결** | 영상 기획·스토리보드에서 자산을 레퍼런스로 활용 | ⬜ 설계 완료, 구현 필요 (§9.5) |

| **사용자 인앱 크레딧 신청 폼** | 사용자가 마스터에게 크레딧을 신청하는 인앱 흐름 | ⬜ 설계 완료, 구현 필요 (§9.7) |

### 1.3 설계 원칙 (경량화)
- **경량 브랜치**: REMO 본체의 다중 조직/의뢰 매칭 등 무거운 개념은 도입하지 않는다. 3-Tier(리모 → 오픈놀 마스터 → 가입 사용자)로 단순화 유지.
- **관제형 SaaS**: 사용자 수 소프트 캡(운영 정책)과 크레딧 지급 마스터 통제로 비용/사용량을 관제.
- **텍스트 우선**: 자산은 항상 선택 사항. 자산 없이도 전체 워크플로우 정상 작동.

## 2. 배경과 문제 정의

### 2.1 현재 제품의 강점
- 영상 기획이 한 줄 텍스트에서 시작해 진입 장벽이 낮다.
- Google OAuth 로그인이 구현되어 있다.
- 신규 가입자 크레딧 초기화 로직이 데이터베이스 마이그레이션에 반영되어 있다.
- 스토리보드 이미지 생성 시 최대 5장의 레퍼런스 이미지를 캐릭터·제품·액세서리·배경으로 분류해 전달할 수 있다.
- 마스터 콘솔의 사용자 목록과 크레딧 현황 UI 기반이 있다.

### 2.2 해결해야 할 문제
- 레퍼런스 이미지는 제작 시점에 매번 다시 추가해야 하며 사용자 자산으로 영구 관리되지 않는다.
- 캐릭터나 제품의 여러 시점·표정·형태를 하나의 재사용 가능한 자산으로 묶는 구조가 없다.
- 단건 이미지만 독립적으로 만들고 결과를 다음 제작에 재사용하는 흐름이 없다.
- 영상 기획 단계에서 특정 캐릭터·제품·로고를 명시적으로 선택해 기획과 스토리보드에 일관되게 연결할 수 없다.
- Google 로그인 안내문은 있으나 최초 가입자의 명시적 동의 상태와 약관 버전별 동의 이력이 관리되지 않는다.
- 마스터 화면의 실제 사용자 잔액 조회와 크레딧 지급 서버 로직이 완성되지 않았다.
- 과거 계획의 마스터 계정 생성·정지·비밀번호 재발급은 Google 셀프가입 중심 방향과 맞지 않는다.

## 3. 제품 목표

1. 사용자가 Google 계정으로 간단히 가입하고 필수 동의를 완료하면 **60크레딧**으로 제작을 시작할 수 있게 한다.
2. 기존의 한 줄 영상 기획 경험을 유지하고, 개인 자산 선택은 **항상 선택 사항**으로 제공한다.
3. 사용자별로 완전히 분리된 **개인 자산 보관함**을 제공한다.
4. 캐릭터·제품의 복수 참고 이미지를 하나의 재사용 가능한 자산으로 관리한다.
5. 단건 이미지 제작과 영상 제작이 같은 개인 자산을 공유하게 한다.
6. 오픈놀 마스터가 가입 사용자를 조회하고 **60,000크레딧 지급 누계 한도** 내에서 크레딧을 지급하게 한다.
7. 모든 사용자 데이터와 자산에 서버 측 권한 검증을 적용한다.

## 4. 비목표 및 제외 범위

이번 범위에는 다음 기능을 포함하지 않는다.

- 마스터가 사용자 계정을 **직접 생성**하는 기능
- 사용자 계정의 **정지 또는 활성화** 기능
- 마스터가 사용자 **비밀번호를 재발급**하는 기능
- **이메일/비번 자체 회원가입** (Google OAuth 단일화)
- 마스터가 사용자 크레딧을 **차감**하거나 잔액을 **강제 설정**하는 기능
- **사용자 간 자산 공유** 또는 오픈놀 공용 자산 보관함
- 자산 협업, 댓글, 승인 워크플로우
- 캐릭터 **음성 생성** 및 음성 자산 관리
- 자산 컬렉션의 **다단계 폴더 구조**
- 마케팅 정보 수신 동의
- 모바일 네이티브 앱

### 레거시 처리
- 기존 `profiles.status`, `profiles.login_id` 등의 레거시 컬럼은 호환성을 위해 즉시 삭제하지 않지만 **신규 제품 기능에서는 사용하지 않는다**.
- `master-create-account`, `master-reset-password` Edge Function은 **호출 경로에서 제거하고 폐기 대상**으로 관리한다.
- `send-production-request` Edge Function은 스토리보드 산출물 이메일 발송 기능으로 유지한다.

## 5. 사용자와 권한 (이해관계자)

| 역할 | 대표 계정 수 | 로그인 방식 | 설명 |
|------|--------------|-------------|------|
| **리모 (개발사)** | DB 수동 프로비저닝 | — | 슈퍼관리자. 초기엔 별도 UI 없음. 크레딧 상한(pool) 설정 주체. |
| **오픈놀 (마스터)** | 1 | Google OAuth | `role='master'`. 관리자 콘솔 + 크리에이티브 앱 모두 이용. 크레딧 지급 승인 주체. |
| **사용자 (크리에이터/소상공인)** | 운영 정책상 소프트 캡(예: 30명, 조정 가능) | Google OAuth | `role='user'`. 크리에이티브 앱만. 개인 자산 보유. |

### 5.1 일반 사용자
- Google 계정으로 로그인한다. 로그인 버튼 하단의 이용약관·개인정보처리방침 링크 노출로 **암묵 동의** 처리한다.
- 한 줄 텍스트만으로 영상 기획을 시작할 수 있다.
- 본인의 자산만 생성·조회·수정·삭제할 수 있다.
- 본인의 자산을 단건 이미지와 영상 제작에 선택적으로 사용한다.
- 본인의 크레딧 잔액과 사용 이력을 확인한다.

### 5.2 오픈놀 마스터
- 일반 사용자와 동일하게 Google 계정으로 로그인한다.
- 서버에 저장된 `profiles.role = 'master'` 권한으로 마스터 기능에 접근한다.
- 가입을 완료한 일반 사용자 목록과 크레딧 정보를 조회한다.
- 사용자에게 크레딧을 지급한다.
- 전체 60,000크레딧 지급 누계와 잔여 지급 가능량을 확인한다.
- 다른 사용자의 개인 자산에는 접근할 수 없다.

> 마스터 권한은 **클라이언트 이메일 비교가 아닌 DB `role` 컬럼과 서버측 `is_master()` RPC**로 강제한다.

## 6. 핵심 제품 원칙

### 6.1 텍스트 우선, 자산은 선택 사항
영상 제작의 기본 진입점은 기존과 동일한 한 줄 아이디어 입력이다. 사용자가 자산을 선택하지 않아도 기획·스토리보드·영상 제작 전 과정이 정상 작동해야 한다.

### 6.2 한 번 만들고 반복 사용
업로드하거나 생성한 시각 자료는 개인 보관함에 저장할 수 있고, 이후 다른 이미지·영상 프로젝트에서 다시 선택할 수 있어야 한다.

### 6.3 제작 흐름 간 일관성
영상 기획 단계에서 선택한 자산은 프로젝트에 연결되고, 기획 프롬프트와 스토리보드 이미지 프롬프트에 계속 반영되어야 한다.

### 6.4 명시적 저장
AI 생성 결과는 자동으로 영구 보관하지 않는다. 사용자가 **`보관함에 저장`**을 선택했을 때만 개인 자산으로 저장한다.

### 6.5 서버가 권한과 크레딧을 판정
자산 소유권, 마스터 역할, 크레딧 잔액과 지급 한도는 클라이언트 상태를 신뢰하지 않고 **DB 정책(RLS) 또는 서버 함수**에서 검증한다.

## 8. 계정 & 인증 아키텍처

### 8.1 로그인 정책 및 진입 시퀀스
- **Google OAuth 단일 진입**. 사용자·마스터 모두 동일한 Google 로그인 사용.
- **이메일/비번 자체 회원가입은 폐기** (합성 이메일 `@sodam.local` 방식 및 실이메일 이메일/비번 이중화 방안 모두 미도입).
- 마스터 판별은 로그인 방식과 무관하게 `profiles.role='master'` 여부로만 결정. 마스터는 **DB 수동 프로비저닝** (초기 1계정).
- 사용자 상한(예: 30명)은 서버 트리거/RPC에서 `SELECT COUNT(*) FROM profiles WHERE role='user'` 체크로 관리. 상한 값은 `admin_config` 테이블에서 조회.

#### 신규 사용자 진입 시퀀스
```
[랜딩 페이지: Google 로그인 버튼 + 하단 이용약관·개인정보처리방침 링크]
   │  로그인 = 암묵 동의
   ▼
[① Google OAuth]
   │
   ▼ 성공 시 사용자 상한 사전 검사
[② 사용자 상한 게이트]
   ├─ 통과 → profiles 로우 자동 생성 (handle_new_user 트리거) + 60크레딧 멱등 지급
   └─ 초과 → [가입 신청 화면 §9.8] (사용자는 로그아웃 상태로 신청서 작성 → 마스터 승인 대기)
   │
   ▼
[③ 대시보드 진입]
   │
   ▼ 최초 진입 시 오버레이
[④ 인트로 설문 모달 (§9.0)]  ← 6문항, 건너뛰기 가능
   ├─ 응답 제출 → intro_survey_responses INSERT (status='completed')
   └─ 건너뛰기  → intro_survey_responses INSERT (status='skipped')
   → 이후 재로그인·재진입 시 재노출 없음
```

#### 기존 사용자 재로그인 시퀀스
```
[랜딩 페이지] → [Google OAuth] → [대시보드 진입]
   (설문은 이미 완료/건너뜀 상태면 재노출 없음)
```

### 8.2 데이터 모델
```sql
-- 기존 마이그레이션 013_roles.sql에서 확정
ALTER TABLE public.profiles
  ADD COLUMN IF NOT EXISTS role   TEXT NOT NULL DEFAULT 'user'
       CHECK (role IN ('user','master'));
-- 레거시: login_id, status는 유지하되 신규 기능에서 미사용
```
- `is_master()` SECURITY DEFINER RPC로 서버측 권한 재검증.
- 마스터는 DB 수동 프로비저닝: `UPDATE profiles SET role='master' WHERE email=…`

### 8.3 Edge Function 정책
| 함수 | 상태 | 비고 |
|------|------|------|
| `send-production-request` | ✅ 유지 | 스토리보드 산출물 고정 이메일 발송 (`momo.ai.fren@gmail.com`) |
| `master-create-account` | ⛔ **폐기** | 호출 경로 제거. 파일은 아카이브로 유지 가능 |
| `master-reset-password` | ⛔ **폐기** | 호출 경로 제거. 파일은 아카이브로 유지 가능 |
| `master-grant-credit` *(신규)* | ⬜ 필요 | 마스터가 사용자에게 크레딧 직접 지급. `credit_transactions` 감사 로그 기록 |

- 셀프 가입(Google)은 Edge Function 없이 `handle_new_user` 트리거로 처리.
- 클라이언트는 `service_role` 접근 불가.

### 8.4 권한 강제 (신뢰 경계)
- `services/adminConfigService.ts`의 `isMaster()` — **UI 게이팅 전용**.
- 실제 권한은 **DB RLS + `is_master()` RPC**에서 재검증.
- `/master` 라우트는 role 가드 + 서버 이중 검증.

### 9.0 인트로 설문 (대시보드 첫 진입 시 모달)
Google OAuth·약관 동의를 마친 사용자가 **대시보드에 처음 진입할 때** 6문항 설문 모달을 노출한다. 오픈놀·리모의 사용자 세그먼트 파악과 향후 제품 개선 근거로 사용한다. 사용자 경험을 해치지 않도록 **건너뛰기**가 가능하며, 응답 여부와 무관하게 모든 기능에 정상 접근할 수 있다.

| ID | 요구사항 |
| --- | --- |
| SURVEY-01 | 신규 사용자가 대시보드에 최초 진입하는 시점에 설문 모달을 오버레이한다. 설문 이전 다른 화면(대시보드 배경)은 시각적으로 노출되지만 상호작용은 모달 우선. |
| SURVEY-02 | 설문 문항은 §9.0 하단 표를 따른다. **모든 문항은 선택 입력**이며(필수 문항 없음), 최소 1개 문항만 응답해도 제출 가능하다. |
| SURVEY-03 | 모달에는 반드시 **[제출] 버튼**과 **[건너뛰기] 버튼**을 함께 노출한다. 두 액션 모두 모달을 닫고 대시보드 사용을 허용한다. |
| SURVEY-04 | 제출 시 `intro_survey_responses(user_id, status='completed', …)` 로우를 저장한다. 건너뛰기 시 `intro_survey_responses(user_id, status='skipped')` 로우만 저장한다. 두 경우 모두 `user_id` UNIQUE 제약으로 1회만 기록된다. |
| SURVEY-05 | 해당 로우가 존재하는 사용자에게는 이후 어떤 로그인·진입에서도 설문 모달을 **다시 노출하지 않는다**. |
| SURVEY-06 | 이미 가입한 기존 사용자(로우가 없더라도)에게 재설문을 강제하지 않는다. 최초 배포 시점의 기존 사용자에겐 1회 노출 후 스킵 시 로우 저장으로 종료. |
| SURVEY-07 | 사용자는 설문 결과를 앱 내에서 조회·수정하지 않는다(운영 분석 목적). |
| SURVEY-08 | 마스터 콘솔에서 설문 응답 요약(문항별 분포, 응답률, 스킵률)을 조회할 수 있다. 개별 사용자 응답 열람은 마스터 권한으로 제한한다. |
| SURVEY-09 | 설문 문항 개편 시 새 `survey_version`으로 응답을 저장하고, 이미 응답·스킵한 사용자에게 재설문을 강제하지 않는다. |
| SURVEY-10 | 설문 모달은 약관 동의(§9.1)와 달리 앱 접근을 차단하지 않는다. 어떤 상태에서도 대시보드·제작 화면 사용이 가능해야 한다. |

### 9.1 인증과 암묵 동의
로그인 = 이용약관·개인정보처리방침 동의로 간주하는 **암묵 동의(implicit consent)** 방식을 채택한다. 별도 체크박스 팝업/동의 게이트는 두지 않는다.

| ID | 요구사항 |
| --- | --- |
| AUTH-01 | 로그인 방법은 Google OAuth를 유지한다. 랜딩 페이지 진입 즉시 Google 로그인 버튼을 사용할 수 있다. |
| AUTH-02 | 로그인 버튼 **바로 아래**에 "로그인 시 이용약관·개인정보처리방침에 동의한 것으로 간주됩니다"류 안내 문구와 두 문서의 열람 링크(모달)를 노출한다. |
| AUTH-03 | 두 문서는 랜딩 페이지 내 모달로 원문을 열람할 수 있어야 한다. (현행 `LandingPage.tsx`의 privacyModal/termsModal 재사용) |
| AUTH-04 | 최초 로그인 성공(=가입 완료) 시 60크레딧을 **한 번만** 자동 지급한다. `credit_transactions.type='signup_bonus'`로 감사 로그 저장. |
| AUTH-05 | OAuth 콜백 재시도·새로고침·중복 요청으로 프로필·크레딧이 중복 생성되지 않아야 한다. (`handle_new_user` 트리거의 멱등화) |
| AUTH-06 | 사용자 상한(운영 정책값) 초과 가입은 즉시 거부·로그아웃 후 **가입 신청 화면(§9.8)**으로 안내한다. |
| AUTH-07 | 약관/개인정보처리방침이 개정될 경우 **문구·문서 내용만 갱신**한다. 재동의 팝업은 노출하지 않는다. |
| AUTH-08 | 기존 사용자의 크레딧·프로젝트·자산은 인증 흐름 변경으로 손실되지 않는다. |

| MASTER-05 | 마스터 전체 지급 누계 한도는 **60,000크레딧**이다. (직접 지급·신청 승인 합산) |

| MASTER-07 | 사용자가 지급받은 크레딧을 소비해도 마스터의 지급 가능 한도는 회복되지 않는다. |
| MASTER-08 | 지급량은 1 이상의 정수이며 지급 사유는 필수다. |
| MASTER-09 | 사용자 잔액 변경, 지급 누계 검증과 거래 이력 기록은 서버에서 **원자적으로** 처리한다. |
| MASTER-10 | 60,000크레딧을 초과하는 동시 지급 요청도 DB 수준에서 차단한다. |
| MASTER-11 | 계정 생성, 정지·활성화, 비밀번호 재발급, 크레딧 차감·강제 설정 UI를 제공하지 않는다. |
| MASTER-12 | 마스터 자신의 제작 크레딧은 **pool과 무관, 무제한(대형 상수)**. 마스터는 관제 대상 밖. |
| MASTER-13 | 마스터 콘솔에 **크레딧 신청 대기함**을 제공한다. `pending` 신청 건수 뱃지 노출, 각 건에 대해 승인·반려·조정 승인이 가능해야 한다. |
| MASTER-14 | 승인/반려 시 반드시 **처리자(reviewer), 처리시각(reviewed_at), 처리 메모**가 기록된다. |
| MASTER-15 | 신청 승인은 §9.7 흐름으로 처리되며, MASTER-05~10 한도·원자성 정책을 그대로 준수한다. |

### 9.7 사용자 인앱 크레딧 신청
사용자가 크레딧 부족 상황에서 마스터에게 크레딧을 요청할 수 있는 흐름. 마스터 직접 지급(§9.2)과 병행 제공.

| ID | 요구사항 |
| --- | --- |
| REQUEST-01 | 사용자는 헤더/설정 화면에서 언제든 `크레딧 신청` 화면에 진입할 수 있으며, 크레딧 잔액 부족으로 생성 실행이 막힌 시점에도 신청 진입점을 노출한다. |
| REQUEST-02 | 신청 폼 필수 입력은 **요청 크레딧 수량(양의 정수)**, **사유 텍스트**다. 첨부 파일(이미지 최대 3장, 각 5MB)은 선택. |
| REQUEST-03 | 동일 사용자의 `pending` 신청은 **최대 1건**만 허용한다. 두 번째 신청은 서버에서 거부하고 기존 신청 상태를 안내한다. |
| REQUEST-04 | 신청 즉시 `credit_requests` 로우가 `status='pending'`으로 생성되며 마스터 대기함에 노출된다. |
| REQUEST-05 | 사용자는 본인의 신청 이력(pending·approved·rejected)과 각 건의 처리 메모를 조회할 수 있다. |
| REQUEST-06 | 사용자는 `pending` 상태의 신청을 스스로 **취소**할 수 있다(`status='cancelled'`). 승인/반려된 건은 취소 불가. |
| REQUEST-07 | 마스터가 승인 시 지급량은 신청량과 다를 수 있다(조정 승인 허용). 실제 지급량은 마스터가 입력한 값을 사용한다. |
| REQUEST-08 | 승인 처리는 **마스터 pool 잔여 한도 검증 → user_credits 증액 → credit_transactions insert → credit_requests.status='approved'** 을 단일 DB 트랜잭션으로 처리한다. |
| REQUEST-09 | 반려 시 status='rejected'와 반려 사유(리뷰어 메모)를 기록한다. 사용자 잔액은 변경하지 않는다. |
| REQUEST-10 | 승인/반려 결과는 사용자 다음 진입 시 배지/토스트로 알린다. 별도 이메일 발송은 이번 범위에 포함하지 않는다. |
| REQUEST-11 | `credit_requests` 테이블은 RLS로 `user_id = auth.uid()` 인 로우 또는 `is_master()`인 세션에만 노출한다. |
| REQUEST-12 | 사용자 인앱 신청 승인분은 마스터 직접 지급분과 **동일한 60,000 pool**을 공유한다. 별도 pool을 두지 않는다. |

#### 사용자 신청 → 마스터 승인 흐름
```
[사용자] 인앱 크레딧 부족 감지 또는 자발적 신청
   └─▶ [신청 폼] 요청 수량 + 사유 + (선택)첨부
         └─▶ credit_requests INSERT (status='pending', user_id=self)
               └─▶ [마스터 콘솔 대기함] 신규 배지
                     ├─ 승인 (지급량 조정 가능)
                     │    ├─ 마스터 pool 잔여 확인 (60,000 - manual_grant 누계)
                     │    ├─ user_credits.balance 증액
                     │    ├─ credit_transactions INSERT (type='manual_grant')
                     │    └─ credit_requests UPDATE status='approved', reviewer, reviewed_at
                     └─ 반려 (사유 필수)
                          └─ credit_requests UPDATE status='rejected', reviewer, reviewed_at
```

### 9.8 사용자 상한 초과 시 가입 신청
사용자 상한(§8.1)이 가득 찬 상태에서 신규 방문자가 Google OAuth를 시도하면, 시스템은 로그인은 성공시키되 **`profiles` 로우를 생성하지 않고** 즉시 로그아웃한 뒤 가입 신청 화면으로 안내한다. 신청자는 마스터 승인 후 재로그인으로 가입을 완료한다.

| ID | 요구사항 |
| --- | --- |
| WAITLIST-01 | 사용자 상한 초과가 감지된 신규 Google 사용자는 프로필이 생성되지 않고 즉시 세션에서 로그아웃된다. |
| WAITLIST-02 | 대신 **가입 신청 화면**을 노출하며, Google에서 획득한 email·display_name을 폼에 기본 채운다. 신청자는 연락처·사유를 추가 입력한다. |
| WAITLIST-03 | 신청서 제출 시 `signup_requests` INSERT (status='pending')을 수행한다. 동일 이메일의 pending 신청이 이미 있으면 서버가 거부하고 기존 상태를 안내한다. |
| WAITLIST-04 | 마스터 콘솔에 **가입 신청 대기함**을 제공한다. 마스터는 각 신청을 승인 또는 반려한다. 사유(reviewer_note)는 필수. |
| WAITLIST-05 | 승인 시 마스터는 사용자 상한을 1 증분(또는 임시 화이트리스트 등록)한다. 이 처리는 서버에서 원자적으로 수행되며 `signup_requests.status='approved'` 로 갱신한다. |
| WAITLIST-06 | 승인 후 신청자가 Google OAuth로 재로그인하면 §8.1 통상 신규 플로우로 진입한다 (상한 게이트 통과 → 약관 동의 팝업 → 대시보드). |
| WAITLIST-07 | 반려 시 `signup_requests.status='rejected'` 로 갱신하고 재신청 정책(예: 30일 후 가능)을 안내한다. |
| WAITLIST-08 | 승인/반려 결과 통보는 마스터가 신청서에 남긴 이메일로 이번 범위에서는 **수동 회신**으로 처리한다(자동 이메일 발송은 후속 과제). |
| WAITLIST-09 | 이미 가입한 사용자가 상한 초과 이후 재로그인해도 정상 진입한다(WAITLIST 흐름은 신규 사용자에만 적용). |

#### 흐름
```
[신규 사용자] Google OAuth
   │
   ▼ 서버가 상한 사전 검사
[사용자 상한 초과 감지]
   │
   ▼ 프로필 미생성 + 세션 종료
[가입 신청 화면]
   │  Google email/name 기본값 + 연락처·사유 입력
   ▼
signup_requests INSERT (status='pending')
   │
   ▼
[마스터 대기함]
   ├─ 승인 → 상한 증분 + status='approved'
   │        신청자가 재로그인하면 §8.1 통상 진입
   └─ 반려 → status='rejected' + reviewer_note
```

### 11.2 기존 데이터 재사용
- `profiles`: Google 사용자 프로필과 `role`을 재사용. `login_id`, `status`는 레거시 유지·미사용.
- `user_credits`: 현재 잔액과 최대 크레딧 데이터를 재사용.
- `credit_transactions`: 가입 지급, 마스터 직접 지급, 신청 승인 지급, 생성 차감, 환불 이력 저장.
- `projects`: 기존 영상 프로젝트 유지.
- `admin_config`: 마스터 총 지급 한도 `60000`, 사용자 상한(운영값)을 저장.

> 마스터 지급 누계는 `credit_transactions`에서 `type = 'manual_grant'`인 양수 거래의 합으로 계산한다. **직접 지급과 신청 승인 지급은 동일한 `manual_grant` 타입을 공유**하되, 신청에서 파생된 지급은 `related_request_id`로 원 신청 로우를 참조한다. 가입 보너스는 `type = 'signup_bonus'`로 구분해 누계에서 제외한다. 지급과 누계 검증은 전용 서버 RPC로 처리한다.

## 12. 권한과 보안 요구사항

- 모든 제작 화면은 인증과 **최신 필수 동의**를 확인해야 한다.
- 마스터 UI 노출 여부와 무관하게 모든 마스터 API가 `is_master()` 또는 동등한 서버 검사를 수행해야 한다.
- 일반 사용자는 다른 사용자의 프로필 목록, 크레딧, 거래 이력과 자산을 조회할 수 없어야 한다.
- 마스터는 사용자·크레딧 운영 정보에는 접근할 수 있지만 **개인 자산 파일에는 접근할 수 없어야** 한다.
- 자산 조회·수정·삭제는 `owner_id = auth.uid()` 조건을 DB RLS에서 강제한다.
- Storage 객체 경로는 사용자 ID로 분리하고 Storage 정책에서도 소유권을 검사한다.
- 업로드 파일의 MIME 형식·용량·확장자를 서버에서 검증한다.
- AI API 키와 외부 서비스 비밀키를 브라우저로 전달하지 않는다.
- 크레딧 차감·환불·지급은 재시도 키 또는 동등한 **멱등성 장치**를 사용해 중복 거래를 막는다.
- 동의 기록은 사용자가 자산을 삭제하더라도 법적·운영 보존 정책에 따라 별도로 관리한다.

## 13. 상태와 예외 처리

| 상황 | 기대 동작 |
| --- | --- |
| OAuth 콜백 재시도·새로고침 | `handle_new_user` 트리거 멱등화로 profiles·60크레딧이 중복 생성되지 않고 성공 상태를 유지한다. |
| 사용자 상한 초과 신규 가입 | 프로필 미생성·즉시 로그아웃 후 §9.8 가입 신청 화면으로 이동. |

| 인트로 설문 모달 건너뛰기 | `intro_survey_responses(status='skipped')` 로우가 저장되어 이후 재노출되지 않는다. 앱 기능은 정상 사용 가능. |
| 이미지 생성 중 잔액 변경 | 서버가 최종 잔액을 검증하고 부족하면 생성 요청을 시작하지 않는다. |
| 이미지 API 실패 | 실패 원인을 표시하고 크레딧을 차감하지 않거나 자동 환불한다. |
| 마스터 한도 초과 지급 | 지급 전체를 거절하고 사용자 잔액과 거래 이력을 변경하지 않는다. |
| 두 마스터 지급 요청이 동시에 한도를 초과 | DB 트랜잭션 잠금 또는 원자 조건으로 하나 이상을 거절한다. |
| 자산 파일 업로드 실패 | 자산 메타데이터와 고아 파일이 남지 않게 롤백 또는 정리한다. |
| 삭제된 자산이 프로젝트에 연결됨 | 프로젝트는 열리지만 삭제 자산을 알리고 새 자산 선택을 안내한다. |
| 자산이 없는 사용자 | 빈 보관함 안내와 업로드·이미지 만들기 진입점을 제공한다. |
| 이미 pending 신청이 있는 사용자가 재신청 | 서버가 거부하고 기존 신청 상태·처리 예정 안내를 반환한다. |
| 크레딧 신청 승인 시 마스터 pool 초과 | 트랜잭션 전체를 롤백하고 신청은 `pending` 유지, 마스터에게 잔여량 부족을 안내한다. |
| 사용자가 승인된 신청을 취소 시도 | 취소 불가 안내(REQUEST-06). status는 그대로 유지. |
| 사용자 자체 신청 취소 (pending) | status='cancelled'로 전환하고 마스터 대기함에서 제외한다. |

## 16. 수용 기준

### 16.1 가입
- 랜딩 페이지에서 Google 로그인 버튼을 즉시 사용할 수 있다.
- 사용자 상한이 가득 찬 상태에서 신규 Google 사용자가 로그인 시도 시 프로필이 생성되지 않고 즉시 로그아웃되며 **§9.8 가입 신청 화면**으로 이동한다. 신청 폼 제출로 `signup_requests(status='pending')` 로우가 생성된다.
- 랜딩 페이지의 로그인 버튼 아래에 이용약관·개인정보처리방침 링크가 노출되고, 링크 클릭 시 각 문서 원문 모달이 열린다.
- Google 로그인 완료 시 잔액이 정확히 **60크레딧**이 된다 (별도 동의 팝업 없음).
- 동일 계정으로 여러 번 로그인해도 가입 보너스는 한 번만 지급된다.
- 신규 사용자는 대시보드 최초 진입 시 **인트로 설문 모달**을 만난다. **제출하거나 건너뛰거나 모두 이후 재노출되지 않는다**. 설문 노출 여부와 무관하게 대시보드·제작 화면은 정상 사용 가능하다.

### 16.2 마스터
- 일반 사용자가 마스터 URL이나 RPC를 직접 호출하면 접근이 거절된다.
- 마스터 사용자 목록의 이메일·이름·가입일·잔액이 실제 데이터와 일치한다.
- **59,990크레딧을 지급한 상태에서 11크레딧 추가 지급은 실패**하고 어떤 잔액도 변경되지 않는다.
- 사용자가 지급받은 크레딧을 모두 사용해도 마스터 잔여 지급 가능량은 증가하지 않는다.
- 사용자 화면에 계정 생성, 정지·활성화, 비밀번호 재발급, 차감·잔액 설정 동작이 존재하지 않는다.

### 16.3 자산 보관함
- 사용자 A가 생성한 자산은 사용자 B의 목록과 직접 API 호출 모두에서 보이지 않는다.
- 캐릭터와 제품 자산에 대표 이미지와 추가 참고 이미지를 저장하고 순서를 변경할 수 있다.
- 로고 원본을 저장하고 다음 이미지 또는 영상 제작에서 선택할 수 있다.
- 자산 이름 검색과 분류 필터가 함께 작동한다.
- 자산 삭제 시 연결 프로젝트 수를 표시하고 확인 전에는 삭제하지 않는다.

### 16.4 단건 이미지
- 자산을 선택하지 않고 프롬프트만으로 이미지 1장을 생성할 수 있다.
- 개인 자산을 선택해 해당 자료를 레퍼런스로 이미지 1장을 생성할 수 있다.
- 생성 전에 비용을 확인할 수 있고 잔액 부족 시 생성할 수 없다.
- 성공 결과를 새 자산 또는 기존 캐릭터·제품의 참고 이미지로 저장할 수 있다.
- 저장하지 않은 생성 결과가 자산 보관함에 자동 등록되지 않는다.

### 16.5 영상 제작
- 자산을 하나도 선택하지 않고 기존 한 줄 아이디어 흐름을 끝까지 진행할 수 있다.
- 자산을 선택한 경우 해당 이름과 설명이 기획 결과에 반영된다.
- 같은 캐릭터 자산이 프로젝트의 여러 스토리보드 이미지 생성 요청에 반복 전달된다.
- 자산 이미지와 장면별 임시 레퍼런스의 합이 모델 입력 한도를 넘으면 정해진 우선순위로 최대 5장만 전달된다.

- **사용자 인앱 크레딧 신청 폼 (§9.7)**: `credit_requests` 스키마, 사용자당 pending 1건 강제, 신청·취소·이력 조회 UI
