0이 문서의 목적

소담에이아이스튜디오(오픈놀) 버전 = 마스터/발급계정 체계 + 아이디·비번 인증 + 크레딧·의뢰 관리 콘솔을 기존 앱 위에 얹는 작업입니다.

본 문서는 개발팀·대표님과 함께 ① 스키마 마이그레이션이 어디까지 필요한지, ② 착수 전 결정할 항목을 판단하기 위한 논의 자료입니다. (하단 §6 결정 필요 항목 참조)

2핵심 판단 — 스키마 마이그레이션 필요한가?

요약: 대규모 마이그레이션은 불필요합니다. 기존 user_credits · credit_transactions · production_requests · projects를 전면 재사용하고, 변경은 대부분 기존 profiles에 컬럼 몇 개 추가(ALTER) 수준입니다. 새 테이블은 0~1개 사이에서 선택하면 됩니다.

현재 스키마 (그대로 활용)

재사용 변경 없음 ALTER 컬럼 추가 신규 새로 필요
테이블상태내용 / 필요한 변경
profilesALTERrole(master/user) 필수, username, status(active/suspended) 추가. (선택) master_id — 단일 마스터라 생략 가능
production_requestsALTERrecipient_email 컬럼 1개 추가(고정 주입). 나머지 그대로
user_credits재사용변경 없음. 신규계정 기본 60 유지
credit_transactions재사용type=manual 이미 존재 → 마스터 부여/사용이력 그대로
projects재사용변경 없음
admin_config재사용키값 저장소. 아래 quota 저장 옵션에 활용 가능
masters신규(선택)credit_quota / allocated 저장용. 안 만들 수도 있음(아래 참조)

마스터 부여 한도(6만) 저장 위치 — 두 옵션

옵션 A — 새 테이블 없음 (최소)옵션 B — masters 테이블 1개
방식admin_config에 master_credit_quota=60000 키값. 부여 누계는 credit_transactions의 manual 합계로 계산masters(id, name, credit_quota, allocated) 단일 행
장점신규 테이블 0개. 마이그레이션 최소의미 명료, 향후 다중 마스터 확장 용이, 조회 단순
단점quota 로직이 config+집계에 흩어짐테이블 1개 추가(그래도 소규모)
→ 논의 포인트 (개발팀·대표): “새 테이블 0개(옵션 A)”로 최소화할지, “masters 테이블 1개(옵션 B)”로 깔끔하게 갈지. 어느 쪽이든 대규모 마이그레이션이 아니며, 실제 난이도의 핵심은 스키마가 아니라 인증 교체(§3-WS2)입니다.

3구현 범위 (5개 워크스트림)

S 작음M 보통L 큼/리스크
WS난이도내용주요 산출
WS1 · 스키마S profiles ALTER(role/username/status), production_requests ALTER(recipient_email), (선택) masters 테이블, RLS 정책 확장 마이그레이션 SQL 1~2개
WS2 · 인증 교체L Google OAuth 제거 → 아이디/비번({아이디}@도메인 합성이메일). 셀프가입 UI 삭제. 계정 생성은 service-role Edge Function(마스터만). 임시 비번 자동생성·재발급. handle_new_user 트리거 정비 authStore 교체, 로그인 화면, create-account Edge Function

WS4 · 라우팅·콘솔 UIM role 가드(App.tsx) + 사이드바 [관리자 콘솔] 진입점(master만, 기존 isAdmin 패턴 확장). /master 콘솔 5화면(대시보드·계정·크레딧·사용이력·의뢰). 워크플로우 한글 라벨 ko.json 반영 마스터 콘솔 컴포넌트, 라우트 가드
WS5 · 의뢰S 제출 시 recipient_email 고정 주입(서버). 마스터 의뢰 조회는 기존 admin_get_all_requests 재사용 제출 로직·조회 화면 연결

4리스크 & 유의점

  • L 인증 전환이 최대 리스크. Google OAuth 제거·Supabase provider 설정·세션·비번 재설정 흐름. 기존 로그인 사용자 영향 검토 필요.
  • M 마스터 제작 시 크레딧 출처 미결. 마스터도 앱에서 제작 → 개인 크레딧에서 빠지나, 6만 풀에서 빠지나? 로직에 직접 영향 → 결정 필요.
  • M 기존 데이터/배포 형태. 신규 빈 DB로 시작인지, 기존 Supabase 데이터 이전인지에 따라 마이그레이션 절차 달라짐.
  • S 임시 비번 전달 방식(마스터 화면 표시 vs 이메일 발송)에 따라 UX·보안 상이.

6결정 필요 항목 (개발팀·대표)

① 스키마 범위
새 테이블 0개(옵션 A · admin_config) vs masters 테이블 1개(옵션 B). — 권장: 단일 마스터라 A도 충분하나, 명료성·확장성 원하면 B
② 마스터 제작 크레딧 출처
마스터가 앱에서 제작 시 (a) 마스터 개인 크레딧 차감 vs (b) 6만 부여 풀에서 차감 vs (c) 마스터는 무제한 — 로직·정산에 직접 영향
③ 배포 형태
신규 빈 DB로 시작 vs 기존 Supabase 데이터 이전 — 기존 Google 가입 사용자 처리 포함
④ Supabase 프로젝트
기존 프로젝트 재사용 vs 소담 전용 신규 프로젝트(권한·데이터 격리)
⑤ 임시 비번 전달
마스터 화면에 1회 표시(복사해 전달) vs 계정 이메일로 발송 — 발급계정에 이메일이 있나? 없으면 화면 표시
⑥ 로그인 아이디 도메인
합성이메일 도메인 확정(예: {아이디}@sodam.local). 실제 메일 수신 불필요
